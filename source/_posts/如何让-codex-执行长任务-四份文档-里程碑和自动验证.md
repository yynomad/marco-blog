一个想法交给 Codex，它很快就能写出第一版代码。任务稍微长一点，新的问题就来了：做到哪里了？为什么选这个方案？测试真的跑过了吗？下一次打开项目，还能不能接着做？

上一篇 用 AI 做项目的一些思考 聊了先确认需求、用 Git 留版本、让 AI 自测和自己验收。这篇继续往前走一步：如果一个项目需要持续做很多轮，怎样让 Codex 按约定推进，也方便我们随时接手？

OpenAI 的长任务案例也采用了四份 Markdown 文档，配合逐里程碑验证和状态更新。这是一种有参考价值的组织方式，适合按项目需要调整。官方长任务案例

## 先把第一版的终点说清楚

还是拿 TXT 阅读器举例。“做个阅读器”留下的空间太大：支持什么格式、怎么翻页、要不要书签，都会影响实现。

可以先把第一版限定为：桌面应用，只支持 UTF-8 编码的 TXT；可以选择文件、显示正文、纵向滚动；导入失败时有明确提示。EPUB、分页、书签和主题设置留到以后。

然后把验收条件写得具体一些：

- 正常 TXT 文件能导入，中文和换行显示正确。
- 空文件有明确提示，应用可以继续操作。
- 读取失败时展示错误，并允许重新选择文件。
- 应用可以启动，核心流程通过相关测试和实际操作验证。
让 Codex 先检查已有仓库，再问那些会改变产品方向的问题。一次问一个关键问题，附上建议和理由，用户回答起来会轻松一些。能从文件确认的技术事实直接检查；可逆的实现选择采用合理默认值并记录。

当目标用户、核心流程、范围、硬约束和验收方式已经清楚，就可以结束这一轮澄清。技术可行性仍不确定时，可以先约定一个小实验，把实验结果补进计划，再确认正式开发的范围。

## 四份文档，各自管一件事

项目里可以放这样的结构：

```plain text
AGENTS.md
docs/
├── Prompt.md
├── Plan.md
├── Implement.md
└── Documentation.md
```

Prompt.md 写清楚最终要交付什么，也写清楚这一版暂时不做什么。需求发生实质变化时，先更新它、记录原因，再确认新的范围。

Plan.md 把工作拆成可以验证的步骤。验证命令集中维护在这里，其他文件引用它，避免复制几份以后内容不一致。

Implement.md 约定执行方式：怎样选下一个里程碑、怎样处理失败、什么时候更新文档、什么情况下需要用户做决定。

Documentation.md 给人看当前状态。写下已经完成的工作、下一步、阻塞、方案选择的原因，以及怎样启动和演示项目。它应当与代码和提交记录对应。

这四份文件可以很短。需求、验证命令和进度各有明确的维护位置，后面就更容易保持一致。

## 把里程碑拆成能实际演示的结果

对于阅读器，我会这样拆第一版：

每个里程碑都写目标、验收标准、测试要求和验证方式。把测试安排进每一步，最后一个里程碑再做完整回归和交付检查。

验证命令要来自真实项目。仓库已经有测试和构建脚本，就检查并复用；新项目尚未配置时，在 M0 建立它们，再把实际命令补进去。文档里可以区分“计划配置”和“已经验证可运行”。

构建通过，只能证明构建这一步成功。阅读器最终还要实际导入文件，检查显示和失败处理。对于界面项目，最好让 Codex 能启动应用、操作界面并查看错误；暂时无法检查的部分明确记录为待验收。

## 确认范围后，让它按循环继续

文档生成后，先查看第一版的范围、验收条件和检查点。确认这些约定，再开始开发。

默认执行循环可以是：

```plain text
选择第一个未完成里程碑
→ 实现最小改动
→ 编写或更新相关测试
→ 运行验证
→ 修复失败并重新验证
→ 更新进度和决策
→ 创建对应的 Git commit
→ 继续下一个里程碑
```

普通里程碑验证通过就继续推进。需要人工看效果的节点提前标出来，比如核心阅读界面完成后看一次，最终交付再走一遍 Demo。

这样，机器可以检查的部分由 Codex 持续处理，你把时间放在产品取舍和实际体验上。

执行规则还要写清楚：不能为了宣布完成而删除测试、放宽验收条件或隐藏失败。遇到环境问题、原有故障和本次改动引入的问题，要分别记录。修复不了时说明原因、已有证据和需要的帮助；不受阻塞影响的工作可以继续。

Git commit 放在一次可验证改动完成之后。提交应包含对应实现、相关测试和必要的文档更新，便于追踪和回滚。

## 用 Skill 复用流程，用 AGENTS.md 留入口

如果只做一次项目，把这套要求写进任务提示词就够了。经常启动新项目，可以把澄清、文档生成和执行约定封装成一个 docs-bootstrap Skill。

Skill 支持显式选择，也可以根据描述匹配任务。SKILL.md 需要 YAML 元数据，包含 name 和 description；完整指令和参考文件按需要加载。创建时可以使用内置的 Skill Creator，再验证当前环境是否发现了它。官方 Skill 文档

一个简单的目录结构如下：

```plain text
docs-bootstrap/
├── SKILL.md
└── assets/
    ├── prompt-template.md
    ├── plan-template.md
    ├── implement-template.md
    └── documentation-template.md
```

模板保存每份文档需要覆盖的字段，具体内容由 Codex 根据项目填写。Skill 的描述要明确适用场景，正文则约定生成哪些文件、何时确认、怎样执行和恢复。先做一个简短版本，用真实项目验证后再调整。

当前官方文档列出的用户级本地目录是 ~/.agents/skills/，项目级目录是 .agents/skills/。实际安装时，以当前环境能够发现的位置为准，并检查能否选择和调用这个 Skill。本地 Skill 发现规则

AGENTS.md 留项目里的简短入口，例如：

```markdown
## 长任务工作约定

- 新项目和复杂功能采用文档流程；小修复使用已有需求和相关测试。
- 启动、恢复任务或进入新里程碑时，读取相关项目文档，并核对代码与 Git 状态。
- 从 docs/Plan.md 选择第一个未完成里程碑，按 docs/Implement.md 执行。
- 每次改动编写或更新相关测试，验证通过后更新状态并创建对应 Git commit。
- 普通里程碑验证通过后继续；在约定的人工检查点等待验收。
- 范围变化、关键决策或无法解决的阻塞需要用户参与时，说明证据和影响。
```

已有 AGENTS.md 时，把入口合并进去，保留原来的项目规范。Codex 会按全局和项目目录层级发现这些指令；本次运行中新生成的文件，也应主动读取，确保执行约定进入当前上下文。官方 AGENTS.md 文档

Skill 负责复用工作方法，实际持续执行还依赖当前运行环境、工具权限和任务机制。跨运行持续推进或定时唤醒，需要另外配置相应机制；普通工作流文件不会自己发起下一次运行。

## 中断之前，留下能接着做的状态

长任务很可能跨会话进行，所以更新状态的时机包括：里程碑完成、出现阻塞、暂停和交接之前。

可以在 Documentation.md 里维护这样一段：

```markdown
## 当前状态

- 当前里程碑：填写实际进度
- 已完成：列出已经验证的结果
- 未完成：列出仍待实现或验证的部分
- 最近提交：填写实际 commit
- 验证证据：实际命令、结果，以及 Demo 检查情况
- 阻塞：问题、影响范围和需要的帮助
- 下一步：一条可以直接执行的动作
```

没有运行过的检查就写“未运行”，需要人工查看的部分就写“待验收”。恢复工作时，让 Codex 读状态，再对照代码、提交和测试结果核实，接着选择下一步。

如果采用的方案变了，也把原因留下。例如发现原来的文件读取方式阻塞界面，调整实现时记录问题和取舍。下一轮就能知道为什么这样做，减少反复推翻方案。

## 从一个可复制的请求开始

刚开始可以直接把下面这段发给 Codex，先验证流程是否适合自己：

```plain text
我想做一个新项目：[一句话需求]。

先检查已有上下文，澄清会影响产品方向的关键问题，
每次问一个，并给出建议和理由。
目标、范围、约束和验收方式清楚后，生成：
docs/Prompt.md、docs/Plan.md、docs/Implement.md、docs/Documentation.md。
合并更新项目 AGENTS.md，保留已有规范。

里程碑按可以演示的完整流程拆分，每一步安排相关测试。
验证命令来自实际配置；待建立的命令标明状态。
文档完成后检查一致性并提交，等待我确认开发范围。
```

确认后再发：

```plain text
文档已确认，开始执行。

读取执行规则并核对当前代码与 Git 状态。
从 Plan.md 第一个未完成里程碑开始，完成实现、相关测试和验证。
验证失败先修复；通过后更新文档并创建对应提交，再继续下一步。
只在约定的人工检查点或需要我做决定时等待。
交付前验证核心流程，记录实际结果和仍待验收的部分。
```

等 docs-bootstrap 安装并验证可调用后，就可以显式选择它，把重复的流程要求收进 Skill，每次只提供新项目的需求。

四文档适合复杂任务，小改动可以沿用已有计划。做完几个项目后，观察需求是否漂移、测试是否有效、状态能否帮助恢复、人工验收时还剩多少问题，再删掉无效规则或补上真正缺失的约定。
